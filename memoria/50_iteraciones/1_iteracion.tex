\section{1ª Iteración}\label{cap:1_iteracion}

\subsection{Análisis}

Según la planificación (Sección~\ref{cap:planificacionExtensa}), esta primera iteración se centra en el módulo básico del ciudadano, es decir, en la selección de la ciudad (RF-01, RF-02 y RF-04), la consulta de la información general de la Semana Santa y los listados y fichas de cofradías, procesiones, pasos y eventos (RF-05 a RF-08 y RF-11). Sin embargo, al tratarse de la primera iteración, también es en la que se define la base sobre la que se construye el resto del proyecto.

Debido a esto, antes de empezar con el diseño se analizaron los principales problemas que había que resolver, valorando para cada uno de ellos las distintas alternativas posibles y eligiendo la que mejor se adaptaba al proyecto. En este apartado se recogen las decisiones necesarias para construir esta primera base del sistema.

\subsubsection{Problemas planteados y alternativas valoradas}\label{sec:decisionesTecnologicas}

\paragraph{Aplicación para Android e iOS}
El requisito RNF-04 exige que la aplicación funcione tanto en Android como en iOS. Para ello se valoraron tres alternativas: desarrollar dos aplicaciones nativas (una en Kotlin para Android y otra en Swift para iOS), utilizar Flutter o utilizar React Native \cite{reactnative}. Las aplicaciones nativas se descartaron desde el principio, ya que al ser un proyecto desarrollado por una única persona supondría programar y probar todo dos veces sin obtener ninguna ventaja funcional. Entre Flutter y React Native, ambas permiten mantener un único código para las dos plataformas, pero finalmente se optó por React Native, ya que utiliza JavaScript, un lenguaje muy extendido y con una gran cantidad de librerías para las funcionalidades que necesita la aplicación, como los mapas, la geolocalización o las notificaciones. Además, se decidió utilizar Expo \cite{expo} en lugar de configurar React Native de forma manual, siguiendo la recomendación de la propia documentación oficial para quienes empiezan en el desarrollo móvil. Expo ofrece ya integrados los módulos nativos que necesita la aplicación, como la ubicación, las notificaciones o los mapas, permite probar la aplicación directamente en el móvil durante el desarrollo y genera los instaladores en la nube (EAS Build), sin necesidad de instalar y configurar Android Studio y Xcode.

\paragraph{Servidor propio o servicio externo}
En un primer momento se planteó utilizar una plataforma \emph{Backend-as-a-Service} (BaaS) como Firebase, que ofrece ya resueltos la base de datos, la autenticación y el control de acceso, lo que agiliza mucho el desarrollo. La alternativa era desarrollar una API REST propia. Finalmente se optó por la API propia, desarrollada con Spring Boot \cite{springboot}, ya que con Firebase gran parte de estas decisiones las tomaba la propia plataforma, y se perdía precisamente la parte de realizar el diseño de la arquitectura en capas, modelar la base de datos, implementar la autenticación y diseñar la API. Además, de esta forma el proyecto no depende de las condiciones de un servicio externo.

\paragraph{Tipo de base de datos}
Se compararon las bases de datos NoSQL, como Firestore o MongoDB, con una base de datos relacional como PostgreSQL \cite{postgresql}. Se eligió la base de datos relacional porque el dominio del proyecto (Sección~\ref{cap:modelo_de_dominio}) está formado por muchas entidades relacionadas entre sí, como una ciudad con sus cofradías, una cofradía con sus pasos o un evento en el que participan varias cofradías. En una base de datos relacional es la propia base de datos la que garantiza que estas relaciones sean correctas mediante las claves foráneas, mientras que en una NoSQL habría que controlarlo desde el código.

\paragraph{Consulta de información sin conexión}
Para cumplir el requisito RNF-06 se podía desarrollar una caché propia que guardara las respuestas en el móvil, o utilizar una librería que ya lo hiciera. Se eligió TanStack Query \cite{reactquery}, que guarda en el dispositivo la última respuesta de cada consulta y la vuelve a pedir automáticamente cuando hay conexión, evitando tener que programarlo desde cero.

\paragraph{Imágenes y favoritos}
Para las imágenes de las cofradías y de los pasos se valoró subirlas a un servicio de almacenamiento como Firebase Storage \cite{firebasestorage} o guardar únicamente su dirección (URL). Se eligió guardar la URL por ser la opción más sencilla para esta versión, dejando la subida de imágenes como trabajo futuro (Sección~\ref{cap:trabajo_futuro}). En cuanto a los favoritos (RF-14), se valoró guardarlos en el servidor o en el propio móvil, y se optó por guardarlos en el móvil, ya que el ciudadano no tiene ninguna cuenta a la que asociarlos.

\subsection{Diseño}

Una vez elegidas las alternativas en el análisis, en este apartado se explica cómo se ha diseñado cada una de ellas: cómo se organiza el sistema, cómo se guardan los datos, cómo son las pantallas y qué patrones de diseño se han aplicado. 

\subsubsection{Arquitectura del sistema}

La arquitectura de un sistema describe, de forma general, en qué partes se divide y cómo se comunican entre sí. En este proyecto se ha definido una arquitectura \textbf{cliente-servidor con servidor propio}, en la que la aplicación React Native (el cliente\footnote{Cliente: en una arquitectura cliente-servidor, es la parte del sistema con la que interactúa directamente el usuario; en este caso, la propia aplicación instalada en el teléfono móvil.}) se comunica mediante peticiones HTTPS\footnote{HTTPS: versión segura (cifrada) del protocolo HTTP, usado habitualmente para la comunicación entre aplicaciones y servicios en internet.} con la API REST propia (el \emph{backend}\footnote{Backend: la parte del sistema que no ve el usuario directamente, encargada de almacenar los datos, gestionar la lógica de negocio y responder a las peticiones que le hace el cliente.}), desarrollada con Spring Boot. Esta API ofrece un conjunto de \emph{endpoints}\footnote{Endpoint: dirección concreta de una API a la que el cliente envía una petición para realizar una operación determinada (por ejemplo, obtener el listado de procesiones de una ciudad).} organizados por recurso, como \texttt{/ciudades}, \texttt{/cofradias}, \texttt{/pasos}, \texttt{/eventos}, \texttt{/procesiones}, \texttt{/recorridos}, \texttt{/notificaciones} o \texttt{/auth}.

La API es la que contiene toda la lógica de negocio y la única que accede a la base de datos PostgreSQL, de forma que el cliente nunca se comunica directamente con ella.

\paragraph{Estructura del front-end}

El código del cliente se organiza siguiendo una \textbf{arquitectura en capas} \cite{sommerville2015}, en la que el proyecto se divide en varios grupos de carpetas (o \emph{paquetes}), cada uno con una responsabilidad concreta. Cada capa solo puede depender de la capa inmediatamente inferior y nunca al revés, de forma que un cambio en una capa afecta al menor número posible de partes del código y cada capa se puede probar por separado. Las cuatro capas definidas son:

\begin{itemize}
    \item \textbf{UI} (\texttt{screens}, \texttt{components}, \texttt{navigation}): contiene las pantallas que ve el usuario, agrupadas por rol (ciudadano, cofrade, Junta de Cofradías y administrador) siguiendo los diagramas de casos de uso del Capítulo~\ref{cap:analisis} y del Apendice~\ref{cap:casos_de_uso_adicionales}, los componentes visuales que se reutilizan entre pantallas, como los mapas, y la navegación entre pantallas.
    \item \textbf{Application} (\texttt{context}): contiene el estado que comparten varias pantallas a la vez, como la sesión del usuario (\texttt{AuthContext}), la ciudad seleccionada (\texttt{CiudadContext}), el día de la Semana Santa que se está consultando (\texttt{DiaContext}) o los favoritos (\texttt{FavoritosContext}).
    \item \textbf{Data} (\texttt{services}, \texttt{models}, \texttt{utils}): contiene un servicio por cada tipo de información del dominio (\texttt{ciudadService}, \texttt{cofradiaService}, \texttt{procesionService}, \texttt{seguimientoService}, \texttt{pushService}, etc.), que son los únicos que se comunican con la API, los modelos que describen cada objeto del dominio dentro de la aplicación y algunas utilidades, como el cálculo de las fechas de la Semana Santa de cada año.
    \item \textbf{Infrastructure} (\texttt{api}): contiene la configuración del cliente HTTP (\texttt{apiClient}), que añade automáticamente el token JWT a cada petición y avisa a la aplicación cuando la sesión ha caducado, y la caché de TanStack Query (\texttt{queryClient}), que guarda las respuestas en el dispositivo para poder consultarlas sin conexión.
\end{itemize}

\paragraph{Estructura del back-end}

El back-end también se organiza en capas, siguiendo la estructura habitual de una API desarrollada con Spring Boot \cite{sommerville2015}. Esta estructura se define en esta primera iteración y es la que se sigue después con cada nueva entidad del sistema:

\begin{itemize}
    \item \textbf{Controller}: ofrece los \emph{endpoints} REST de cada recurso, recibe las peticiones HTTP, delega el trabajo en la capa de servicio y devuelve la respuesta HTTP correspondiente (código de estado y cuerpo en JSON).
    \item \textbf{Service}: contiene la lógica de negocio, como comprobar que los datos obligatorios de una cofradía están completos o que no se elimina una ciudad que todavía tiene cofradías.
    \item \textbf{Repository}: contiene las interfaces de Spring Data JPA \cite{springdatajpa}, una por cada entidad, que se encargan de acceder a PostgreSQL y cuya implementación genera Spring automáticamente.
    \item \textbf{Security}: contiene la configuración de Spring Security \cite{springsecurity}, que decide qué peticiones necesitan que el usuario se identifique. En esta iteración todas las consultas son públicas, y esta capa se completa a partir de la Iteración 3, cuando aparece el acceso de los cofrades.
    \item \textbf{DTO} (\emph{Data Transfer Object}): contiene las clases que definen exactamente qué datos entran y salen de cada \emph{endpoint}, de forma que no se exponen directamente las entidades de la base de datos y un cambio interno no afecta a lo que recibe el cliente.
\end{itemize}

En esta iteración se aplica a las entidades del módulo de ciudadano (\texttt{Ciudad}, \texttt{JuntaCofradias}, \texttt{Cofradia}, \texttt{Paso} y \texttt{Evento}), y en las siguientes iteraciones el resto de entidades se van añadiendo siguiendo la misma estructura. Por ello, en la Figura~\ref{fig:disenoPaquetesBackend} se muestra el diagrama de paquetes con todas las entidades de la versión final de la aplicación. Además de estas capas, existe un paquete \texttt{exception}, que transforma los errores en respuestas HTTP comprensibles para el cliente, y un paquete \texttt{util} con las clases que no pertenecen a ninguna entidad concreta, como la lectura de los archivos GPX. El esquema completo de la base de datos se detalla en el Apéndice~\ref{cap:esquemaBD}, y su diseño se explica en el apartado \nameref{sec:disenoBD}.

\subsubsection{Diseño de la base de datos}\label{sec:disenoBD}

PostgreSQL \cite{postgresql} es una base de datos \textbf{relacional}, en la que la información se organiza en tablas con filas y columnas, y las relaciones entre entidades se representan mediante \textbf{claves foráneas}\footnote{Clave foránea (\emph{foreign key}): columna de una tabla que referencia la clave primaria de otra tabla, y que la propia base de datos utiliza para garantizar que esa relación siempre apunta a un registro que realmente existe (integridad referencial).}, que la propia base de datos se encarga de validar. Para acceder a ella desde Java se utiliza Spring Data JPA \cite{springdatajpa} junto con Hibernate \cite{hibernate}, un \emph{ORM}\footnote{ORM (\emph{Object-Relational Mapping}): técnica que traduce automáticamente entre los objetos de un lenguaje de programación orientado a objetos (Java, en este caso) y las tablas de una base de datos relacional, evitando escribir manualmente la mayoría de las sentencias SQL.} que evita tener que escribir a mano la mayoría de las consultas SQL.

En esta iteración se definen los criterios con los que se pasa el modelo de dominio de la Figura~\ref{fig:DiagramDomain} a tablas, y que se siguen durante todo el proyecto. Aunque en esta iteración solo se crean las tablas del módulo de ciudadano, algunos ejemplos corresponden a tablas que se añaden más tarde, ya que sirven para explicar mejor cada criterio. Las decisiones propias de cada funcionalidad posterior se explican en el diseño de la iteración correspondiente. Los criterios generales son los siguientes:

\begin{itemize}
    \item Las relaciones de uno a muchos se representan con una clave foránea en la tabla del lado ``muchos''. Por ejemplo, la tabla \texttt{pasos} tiene la columna \texttt{cofradia\_id} y la tabla \texttt{cofradias} tiene la columna \texttt{ciudad\_id}, de forma que para obtener los pasos de una cofradía basta con buscar por esa columna.
    \item Las relaciones de muchos a muchos, como las cofradías que participan en varios eventos o los pasos que participan en varios eventos y procesiones, se representan mediante \textbf{tablas intermedias} (\texttt{eventos\_cofradias} y \texttt{pasos\_eventos}).
    \item La tabla \texttt{ubicaciones} (latitud, longitud y dirección) es independiente y a ella hacen referencia tanto \texttt{eventos} como \texttt{puntos\_ruta}. De esta forma no se repiten estas columnas en cada tabla y se puede reutilizar una misma ubicación, como una iglesia en la que se celebra un evento y por la que pasa una procesión.
    \item Las herencias del modelo de dominio se representan con una \textbf{tabla por cada clase} (estrategia \texttt{JOINED} de JPA): \texttt{procesiones} extiende a \texttt{eventos}, \texttt{puntos\_de\_interes} a \texttt{puntos\_ruta}, y \texttt{administradores} y \texttt{miembros\_junta\_cofradia} a \texttt{usuarios}. El identificador de cada subtipo es a la vez su clave primaria y una clave foránea a la tabla padre, evitando así tener una única tabla con muchas columnas vacías según el tipo.
    \item Los favoritos no tienen tabla, ya que se guardan en el propio móvil, almacenando únicamente el tipo y el identificador del elemento marcado.
\end{itemize}

\subsubsection{Interfaces de usuario}
 
Paralelamente a las decisiones de arquitectura y de base de datos, se ha diseñado en Figma \cite{figma} mediante \emph{mockups}\footnote{Mockup: representación visual estática de la interfaz de una aplicación, sin funcionalidad real, utilizada para planificar el diseño antes de su implementación.} el conjunto de pantallas correspondiente al alcance de esta primera iteración según la planificación (Sección~\ref{cap:planificacionExtensa}): las funcionalidades fundamentales del perfil de ciudadano, es decir, la visualización de la información general de la Semana Santa, el listado de organizaciones y la consulta de eventos. Siguiendo ese mismo criterio, el resto de pantallas de la aplicación, como el mapa en vivo, el modo cofrade o los paneles de la Junta de Cofradías y del administrador, se diseñan en la iteración a la que corresponden según la planificación, y se documentan en el apartado de Diseño de esa misma iteración.

Antes de entrar en el detalle de cada pantalla, esta primera iteración fija también los criterios visuales comunes a toda la aplicación, para que el resto de iteraciones los reutilicen sin tener que redefinirlos: una estética oscura con acentos dorados, que evoca la iluminación de cirios y el ambiente nocturno característico de las procesiones, y una barra de navegación inferior fija con cinco secciones (\emph{Inicio}, \emph{Calendario}, \emph{Mapa}, \emph{Buscar} y \emph{Perfil}), que se corresponde directamente con el paquete \texttt{navigation/} descrito en el apartado de arquitectura. Los listados de cofradías, procesiones, pasos y eventos no tienen una sección propia en la barra de navegación, sino que se accede a ellos desde un menú en la pantalla de \emph{Inicio}, tal y como se explica más adelante.
 
La paleta de color se apoya en tonos marrón muy oscuro, casi negro, para el fondo (\texttt{\#1E1008}, \texttt{\#120A06}, \texttt{\#34150E}, \texttt{\#472F17}), dorados como color de acento para títulos, iconos activos y elementos interactivos (\texttt{\#C9A84C}, \texttt{\#9A7D60}), tonos crema para tarjetas y textos secundarios (\texttt{\#F0E0C8}, \texttt{\#E3D595}) y blanco (\texttt{\#FFFFFF}) para el texto principal sobre fondo oscuro; un verde puntual (\texttt{\#37E37E}) se reserva para indicadores de estado, como una procesión en curso. En cuanto a la tipografía, se combinan tres familias: \textbf{Cormorant Garamond}, una serifa elegante, para los títulos, coherente con la estética evocada; \textbf{Lora}, también serifa pero más neutra, para el texto de lectura extensa (historia de una cofradía, descripción de un paso); y \textbf{Sora}, de palo seco, para los elementos de interfaz (botones, etiquetas, barra de navegación), donde interesa más la legibilidad a tamaños pequeños que el carácter estético. Estas decisiones se apoyan, además del criterio propio, en las pautas de \emph{Material Design~3} \cite{materialdesign3}, la guía de diseño de interfaz de Google, en particular en lo relativo al contraste de color, el tamaño mínimo táctil de los elementos interactivos y la estructura de la barra de navegación inferior.

\subsubsection{Patrones de diseño}

Un patrón de diseño \cite{larman2004} es una solución ya conocida y reutilizable a un problema que se repite con frecuencia en el desarrollo de software, y su uso facilita la legibilidad, el mantenimiento y la escalabilidad del código. Para elegir los patrones de este proyecto se revisaron dos TFG anteriores de la escuela con una arquitectura parecida (una aplicación móvil apoyada en Firebase). De ellos se descartaron los patrones \emph{Builder} y \emph{Abstract Factory}, ya que en Java se utilizan porque los constructores no admiten bien parámetros opcionales, pero en JavaScript basta con un objeto con esos campos opcionales, y además en ningún punto del sistema es necesario intercambiar familias completas de implementaciones. Los seis patrones que se han aplicado finalmente son los siguientes:

\begin{itemize}
    \item \textbf{Singleton}: patrón que garantiza que una clase tenga una única instancia en toda la aplicación y un punto de acceso global a ella, evitando crear copias innecesarias. En este proyecto, el cliente HTTP de la API (\texttt{apiClient}), que añade el token JWT a cada petición, y la caché de TanStack Query (\texttt{queryClient}) se crean una única vez y se reutilizan en toda la aplicación.
    \item \textbf{Repository}: patrón que separa el acceso a los datos del resto de la aplicación, ocultando cómo y dónde se guardan. En el cliente, la capa \texttt{services} es la única que conoce el cliente HTTP de la API, de forma que el resto de la aplicación solo llama a funciones como \texttt{procesionService.getProcesionesEnCurso(ciudadId)}, sin saber que por detrás se está haciendo una petición a la API. En el backend, este patrón se aplica directamente en la capa \texttt{repository}, ya que las interfaces de Spring Data JPA son una implementación del propio patrón Repository. Gracias a esto, se podría cambiar la forma de guardar los datos sin tener que modificar las pantallas ni los controladores.
    \item \textbf{Observer}: patrón en el que uno o varios elementos (observadores) se suscriben a los cambios de otro y reciben un aviso automáticamente cuando este cambia, sin tener que preguntar continuamente. En este proyecto se aplica a la recepción de notificaciones \emph{push}, ya que la aplicación se registra como observadora de las notificaciones que llegan (\texttt{Notifications.setNotificationHandler} de Expo Notifications) y recibe cada una de ellas automáticamente, sin tener que preguntar al servidor si hay alguna nueva. En cambio, este patrón no se aplica a la posición de las procesiones, ya que en ese caso es la propia aplicación la que pregunta al servidor cada 30 segundos.
    \item \textbf{Context/Provider}: mecanismo propio de React (no es un patrón GoF\footnote{GoF (\emph{Gang of Four}): apodo con el que se conoce a los cuatro autores del libro \emph{Design Patterns} \cite{gof} (1994), que popularizó el catálogo clásico de patrones de diseño orientado a objetos (Singleton, Observer, Factory Method, entre otros).} clásico) que permite compartir un dato o un estado con cualquier pantalla de la aplicación sin tener que pasarlo de componente en componente. De esta forma, \texttt{AuthContext}, \texttt{CiudadContext} y \texttt{CofradeContext} comparten con las pantallas que lo necesiten la sesión del usuario, la ciudad seleccionada y si el cofrade está compartiendo su ubicación.
    \item \textbf{Facade}: patrón que ofrece una única función sencilla para realizar una operación que, por detrás, necesita varios pasos. En el caso de uso ``Compartir ubicación durante procesión'' (RF-24), la función \texttt{seguimientoService.iniciarSeguimiento} se encarga de pedir el permiso de ubicación, de enviar periódicamente la posición a la API, incluso con el móvil bloqueado, y de gestionar una posible pérdida de conexión.
    \item \textbf{Adapter}: patrón que convierte el formato de datos de un sistema externo al formato que espera la aplicación, de forma que ambos puedan funcionar juntos sin modificar ninguno de ellos. Al importar el recorrido de una procesión, el backend recibe un archivo GPX, un formato estándar que generan herramientas como gpx.studio, Wikiloc o Strava. La clase \texttt{GpxParser} lee este archivo y lo convierte en la lista ordenada de puntos (latitud y longitud) que necesita \texttt{RecorridoService} para crear el \texttt{Recorrido}.
\end{itemize}

\subsection{Implementación}

Se ha implementado el backend propio descrito en el apartado de diseño anterior: un proyecto Spring Boot~\cite{springboot} generado con Spring Initializr, organizado en los paquetes \texttt{model}, \texttt{repository}, \texttt{service}, \texttt{controller}, \texttt{dto}, \texttt{security} y \texttt{exception} que siguen la estructura de capas ya justificada, y con el esquema de PostgreSQL gestionado mediante migraciones versionadas de Flyway~\cite{flyway} (un script SQL numerado por cada cambio de esquema), en lugar de dejar que Hibernate genere o modifique las tablas automáticamente; así el esquema queda documentado paso a paso y se aplica igual en local, en el servidor de despliegue y en cualquier entorno nuevo, tal y como recoge el manual de despliegue (Apéndice~\ref{cap:manual_despliegue}).

Sobre esa base se han implementado las cuatro capas para todas las entidades necesarias para el módulo de ciudadano de esta primera iteración --\texttt{Ciudad}, \texttt{JuntaCofradias}, \texttt{Cofradia}, \texttt{Paso} y \texttt{Evento}--, cada una con su correspondiente conjunto de \emph{endpoints} REST de consulta y gestión (\texttt{GET}, \texttt{POST}, \texttt{PUT}, \texttt{DELETE}), documentados automáticamente en \texttt{/swagger-ui.html} mediante springdoc-openapi~\cite{springdoc}. \texttt{JuntaCofradias} se implementa en esta misma iteración por ser, igual que \texttt{Ciudad}, un dato base del que depende \texttt{Cofradia} (Apéndice~\ref{cap:esquemaBD}), aunque su gestión efectiva --dar de alta, editar o dar de baja una Junta-- corresponda al panel de administrador de la Iteración 5.

Durante esta implementación se han detectado varias necesidades no recogidas en el diseño inicial de la base de datos, que se han ido resolviendo sobre la marcha y quedan documentadas con su justificación en el Apéndice~\ref{cap:esquemaBD}: entre ellas, que la información de una cofradía y de un paso necesitaba más campos de los previstos inicialmente (\texttt{web} en lugar de un archivo adjunto, \texttt{analisis\_artistico} para el paso), o que \texttt{Cofradia} debía depender de \texttt{Ciudad} y no de \texttt{JuntaCofradias}, para que la información de las cofradías de una ciudad no se viera afectada por una renovación de su Junta.

Queda pendiente para el cierre de esta iteración la implementación de las pantallas de cliente correspondientes sobre esta API, que hasta ahora consumían datos de prueba (\emph{mock}).
